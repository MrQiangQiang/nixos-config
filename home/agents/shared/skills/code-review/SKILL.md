
对 `HEAD` 与用户提供的固定点之间差异的两轴审查：

- **标准**——代码是否符合本仓库文档化的编码标准？
- **规格**——代码是否忠实地实现了来源 issue / PRD / 规格？

两个轴作为**并行子代理**运行，这样它们不会污染彼此的上下文，然后此 skill 聚合它们的发现。

问题跟踪器应该已经提供给你——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定固定点

无论用户说的固定点是什么——commit SHA、分支名、tag、`main`、`HEAD~5` 等等。如果他们没有指定一个，询问。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三点，所以比较是针对 merge-base 的）。也通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在继续之前，确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏的引用或空 diff 应该在这里失败——而不是在两个并行子代理内部。

### 2. 识别规格来源

按以下顺序查找来源规格：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下匹配分支名或功能的 PRD / 规格文件。
4. 如果什么也没找到，询问用户规格在哪里。如果他们说没有，**规格**子代理将跳过并报告"无可用规格"。

### 3. 识别标准来源

仓库中记录应如何编写代码的任何内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库记录的内容之上，标准轴始终携带下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（_Refactoring_，第 3 章），即使仓库什么也没记录也适用。两条规则约束它：

- **仓库覆盖。** 文档化的仓库标准总是优先；当它认可坏味道基线会标记的内容时，抑制该坏味道。
- **始终是判断问题。** 每个坏味道是一个带标签的启发式（"可能的 Feature Envy"），绝不是硬性违规——并且，和这里的任何标准一样，跳过工具已经强制执行的内容。

每个坏味道读作*它是什么* → *如何修复*；将其与 diff 对照：

- **Mysterious Name** — 一个函数、变量或类型的名称没有揭示它做什么或持有什么。→ 重命名它；如果没有诚实的名字出现，设计就模糊了。
- **Duplicated Code** — 相同的逻辑形态在变更中的多个 hunk 或文件中出现。→ 提取共享形态，从两处调用它。
- **Feature Envy** — 一个方法更多地深入另一个对象的数据而非自己的。→ 将该方法移到它羡慕的数据上。
- **Data Clumps** — 相同的几个字段或参数总是一起出现（一个想要诞生的类型）。→ 将它们捆绑成一个类型，传递那个。
- **Primitive Obsession** — 一个原始类型或字符串代表一个值得拥有自己类型的领域概念。→ 给该概念自己的小类型。
- **Repeated Switches** — 对同一类型的相同 `switch` / `if` 级联在变更中反复出现。→ 用多态替换，或两个站点共享的一个 map。
- **Shotgun Surgery** — 一个逻辑变更迫使在 diff 中的许多文件中分散编辑。→ 将一起变更的内容聚集到一个模块中。
- **Divergent Change** — 一个文件或模块因几个不相关的原因被编辑。→ 拆分，使每个模块因一个原因变更。
- **Speculative Generality** — 为规格没有的需求添加的抽象、参数或钩子。→ 删除它；内联回去直到真实需求出现。
- **Message Chains** — 调用方不应依赖的长 `a.b().c().d()` 导航。→ 将遍历隐藏在第一个对象的一个方法后面。
- **Middle Man** — 一个主要只是转发委托的类或函数。→ 切除它，直接调用真实目标。
- **Refused Bequest** — 一个忽略或覆盖大部分继承内容的子类或实现者。→ 放弃继承，使用组合。

### 4. 并行生成两个子代理

发送一条消息包含两个 `Agent` 工具调用。两者都使用 `general-purpose` 子代理。

**标准子代理提示**——包含：

- 完整的 diff 命令和 commit 列表。
- 你在步骤 3 中找到的标准来源文件列表，**加上步骤 3 中的坏味道基线**完整粘贴——子代理没有其他途径访问它。
- 简报："报告——按文件 / hunk 相关处——(a) diff 违反文档化标准的每个地方：引用标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：命名它并引用 hunk。区分硬性违规和判断问题——文档化标准违规可以是硬性的，但基线坏味道始终是判断问题，且文档化的仓库标准覆盖基线。跳过工具强制执行的内容。400 字以内。"

**规格子代理提示**——包含：

- diff 命令和 commit 列表。
- 规格的路径或获取的内容。
- 简报："报告：(a) 规格要求但缺失或不完整的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现但实现看起来错误的需求。为每个发现引用规格行。400 字以内。"

如果规格缺失，跳过规格子代理并在最终报告中注明这一点。

### 5. 聚合

在 `## 标准` 和 `## 规格` 标题下呈现两份报告，逐字或轻度清理。**不要**合并或重新排序发现——两个轴是刻意分开的（见 _为什么两个轴_）。

以一行总结结尾：每个轴的发现总数，以及每个轴内最严重的问题（如果有）。不要跨轴选出唯一胜出者——那是分离旨在防止的重新排序。

## 为什么两个轴

一个变更可以通过一个轴而失败另一个：

- 遵循每个标准但实现错误内容的代码 → **标准通过，规格失败。**
- 完全按照 issue 要求但破坏项目约定的代码 → **规格通过，标准失败。**

分开报告它们防止一个轴掩盖另一个。
