
# 领域建模

在设计时主动构建和打磨项目的领域模型。这是一项*主动*的纪律——挑战术语、构造边界场景，并在术语和决策刚成型的当下就写进术语表和记录中。（仅仅*阅读* `CONTEXT.md` 获取词汇不属于这个 skill——那是任何 skill 都能做的一行习惯。本 skill 用于你正在改变模型时，而非仅仅消费模型时。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则该仓库有多个上下文。该映射指向每个上下文所在位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件——只在有内容要写时才创建。如果不存在 `CONTEXT.md`，在第一个术语确定时创建一个。如果不存在 `docs/adr/`，在需要第一个 ADR 时创建它。

## 会话进行中

### 对照术语表质疑

当用户使用的术语与 `CONTEXT.md` 中的既有语言冲突时，立即指出。"你的术语表把 'cancellation' 定义为 X，但你似乎指的是 Y——到底是哪个？"

### 打磨模糊语言

当用户使用模糊或重载的术语时，提出一个精确的规范术语。"你说的是 'account'——你指的是 Customer 还是 User？这是两个不同的东西。"

### 讨论具体场景

在讨论领域关系时，用具体场景做压力测试。构造场景去探查边界情况，迫使用户精确说明概念之间的边界。

### 与代码交叉验证

当用户陈述某事物的运作方式时，检查代码是否一致。如果发现矛盾，呈现出来："你的代码取消的是整个 Order，但你刚才说部分取消是可能的——哪个才对？"

### 即时更新 CONTEXT.md

当某个术语确定时，立即更新 `CONTEXT.md`。不要攒着批量处理——发生时就记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应当完全不包含实现细节。不要把 `CONTEXT.md` 当作规格、草稿本或实现决策的仓库。它只是术语表，别无他物。

### 谨慎提出 ADR

只有当以下三点都成立时才提出创建 ADR：

1. **难以逆转** —— 日后改变主意的成本是实质性的
2. **没有上下文会令人困惑** —— 未来的读者会想"他们为什么这么做？"
3. **真实权衡的结果** —— 存在真正的备选方案，你出于具体原因选择了其中一个

只要缺少任何一点，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
