
# Ask Matt

你不记得每个 skill，所以问。

一个**流程**是穿过 skills 的路径。大多数路径沿着一条**主流程**运行，两个**入口匝道**并入它。其他一切都是独立的，或者是运行在下面的词汇层。

## 主流程：想法 → 交付

大多数工作行进的路线。你有一个想法并希望它被构建。

1. **`/grill-with-docs`** — 通过访谈磨砺想法。当你**有代码库**时从这里开始：它是有状态的，将所学保留在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me`——见独立。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留下文档痕迹的那个。）
2. **分支——你能在对话中解决每个问题吗？** 如果一个问题需要可运行的答案（状态、业务逻辑、你必须看到的 UI），绕道通过原型，两个方向都由 **`/handoff`** 桥接（见跨越会话）：
   - **`/handoff`** 导出，然后针对该文件打开一个全新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 回你学到的内容，并从原始想法线程引用它。
3. **分支——这是一个多会话构建吗？**
   - **是** → **`/to-spec`**（将线程转为规格），然后 **`/to-tickets`** 将其拆分为 tracer-bullet 工单，每个声明其**阻塞边界**。在本地跟踪器上是 `.scratch/<feature>/issues/` 下每个工单一个文件，按阻塞项优先手工处理；在真实跟踪器上边界成为原生阻塞链接，所以任何阻塞项已完成的工单都可以被认领——每个工单启动 **`/implement`**，**在每个之间清理上下文**。
   - **否** → **`/implement`** 就在这里，在同一个上下文窗口中。

   无论哪种方式，**`/implement`** 通过内部驱动 **`/tdd`** 构建每个 issue——一次一个红-绿切片——然后收尾时运行 **`/code-review`**，对 diff 的两轴审查（标准 + 规格），然后提交。当你只想在没有完整规格的情况下测试优先构建一个具体行为时，单独使用 **`/tdd`**；当你想针对固定点审查分支或 PR 时，单独使用 **`/code-review`**。

### 上下文卫生

将步骤 1–3 保持在一个**不间断的上下文窗口**中——不要压缩或清理，直到 `/to-tickets` 之后——这样磨砺、规格和工单都建立在同一思考上。然后每个 `/implement` 全新开始，从工单工作。

此限制是 **[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍在敏锐推理的窗口（最先进模型上约 120k token）。如果会话在 `/to-tickets` 之前接近它，不要在退化中硬撑——`/handoff` 并在全新线程中继续。

## 入口匝道

一个生成工作然后并入主流程的起始情境。

- **Bug 和请求堆积** → **`/triage`**。它通过分诊角色移动 issue 并产生 agent 就绪的 issue，**`/implement`** 稍后拾取。

  分诊只用于**你不是创建的** issue——bug 报告、传入的功能请求、任何原始到达的内容。`/to-tickets` 产生的工单已经 agent 就绪，所以**不要分诊它们**。

- **某些东西坏了** → **`/diagnosing-bugs`**。对于困难的情况：第一眼就抵抗的 bug、间歇性 flake、在两个已知良好状态之间潜入的回归。它拒绝在拥有**紧密反馈循环**——一条已经在此 bug 上变红的命令——之前进行理论化，然后用回归测试修复。它的事后复盘在真实发现是没有好的接缝锁定 bug 时交给 **`/improve-codebase-architecture`**。

- **一个庞大的、模糊的努力——一个全新项目或庞大的功能构建，太大无法在一个会话中完成** → **`/wayfinder`**。当从这里到目的地的路还不可见时，它在问题跟踪器上绘制一张调查工单的**共享地图**并逐一解决它们——产生**决策，而非交付物**——直到雾被推回，路清晰。然后它在 **`/to-spec`** 并入主流程（或者，如果努力结果足够小，直接到 **`/implement`**）。**`/grill-with-docs`** 磨砺你能在一个会话中把握的想法，wayfinder 用于你无法把握的想法。

## 代码库健康

不是功能工作——维护。

- **`/improve-codebase-architecture`** — 每当你有闲暇时刻运行，以保持代码库对 agent 友好。它浮现**深化机会**；选择一个_生成一个想法_，你可以在 `/grill-with-docs` 带入主流程。它是找到候选者的调查；**`/codebase-design`**（下面）是你设计所选者的工作台。

## 下面的词汇

两个模型调用的引用，运行在其他 skills *之下*——每个是其词汇的唯一真相来源。当**词语**而非流程是问题时，直接求助于它们；或让上面的 skills 拉入它们。

- **`/domain-modeling`** — 磨砺项目的*领域*语言：挑战一个模糊术语，解决一个重载词（"account" 承担三个职责），将一个难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动以保持 `CONTEXT.md` 干净术语表的主动纪律。
- **`/codebase-design`** — 深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的*形状*：大量行为在干净接缝处的小接口背后。`/tdd` 和 `/improve-codebase-architecture` 都说它。

## 跨越会话

- **`/handoff`** — 当一个线程满了或你需要分支出去（例如进入一个 `/prototype` 会话）时，这会将对话压缩成一个 markdown 文件。你不是原地继续——你**打开一个新会话并引用该文件**以携带上下文。它是上下文窗口之间的桥，两个方向都是。当你想要一个**全新会话**但需要**当前对话保留**时使用它。
- **`/compact`**（内置）——留在**同一对话**中，让较早的轮次被总结。在**阶段之间的有意中断**处使用，当你不介意丢失逐字历史时。不要在阶段中间压缩——agent 会迷失方向。`/handoff` 分叉；`/compact` 继续。

## 独立

完全在主流程之外。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的无情访谈，但适用于你**没有代码库**时。无状态：它不在本地保存任何内容，不构建 `CONTEXT.md`。求助于它以磨砺任何不住在仓库中的计划或设计。
- **`/prototype`** — 一个小的一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。从第一天起就是一次性的——保留答案，删除代码。它是主流程步骤 2 中的绕道，但任何时候设计问题难以在纸上解决时求助于它。
- **`/research`** — 将阅读跑腿委托给一个**后台 agent**：它针对**主要来源**调查问题，然后在仓库中留下一个带引用的 Markdown 文件。它阅读时继续工作。它产生的文件是要*带入*主流程在 `/grill-with-docs` 的——研究喂养思考，它不替代思考。
- **`/teach`** — 跨多个会话学习一个概念，使用当前目录作为有状态工作区。
- **`/writing-great-skills`** — 写好和编辑好 skills 的参考。

## 前提条件

**`/setup-matt-pocock-skills`** — 在你的第一个工程流程之前运行，以配置其他 skills 假定的问题跟踪器、分诊标签和文档布局。自定义问题跟踪器也可用。
