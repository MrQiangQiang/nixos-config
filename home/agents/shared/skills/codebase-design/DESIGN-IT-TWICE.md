# 设计两次

当用户想为选定的深化候选探索替代接口时，使用此并行子代理模式。基于"Design It Twice"（Ousterhout）— 你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇表 — **模块**、**接口**、**接缝**、**适配器**、**杠杆作用**。

## 流程

### 1. 框定问题空间

在生成子代理之前，为选定候选写一个面向用户的问题空间解释：

- 任何新接口需要满足的约束
- 它将依赖的依赖，及其所属类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示例代码草图来落地约束 — 不是提案，只是让约束变具体的方式

展示给用户，然后立即进入步骤 2。用户在子代理并行工作时阅读和思考。

### 2. 生成子代理

用 Agent 工具并行生成 3+ 个子代理。每个必须为深化后的模块产出一个**根本不同**的接口。

用各自独立的技术简报提示每个子代理（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）。简报独立于步骤 1 中面向用户的问题空间解释。给每个代理不同的设计约束：

- 代理 1："最小化接口 — 目标是最多 1-3 个入口点。最大化每个入口点的杠杆作用。"
- 代理 2："最大化灵活性 — 支持许多用例和扩展。"
- 代理 3："为最常见的调用者优化 — 使默认情况变得简单。"
- 代理 4（如适用）："围绕端口与适配器设计，用于跨接缝依赖。"

在简报中同时包含 [SKILL.md](SKILL.md) 词汇表和 CONTEXT.md 词汇表，使每个子代理的命名与架构语言和项目领域语言一致。

每个子代理输出：

1. 接口（类型、方法、参数 — 加上不变量、顺序、错误模式）
2. 使用示例展示调用者如何使用它
3. 实现在接缝背后隐藏了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡 — 杠杆作用高的地方，薄的地方

### 3. 呈现并比较

顺序呈现设计使用户能吸收每个，然后用散文比较。按**深度**（接口处的杠杆作用）、**局部性**（变更集中在哪里）和**接缝位置**对比。

比较后，给出你自己的推荐：你认为哪个设计最强及为什么。如果不同设计的元素组合得好，提出一个混合方案。要有主见 — 用户想要一个强的判断，而非一份菜单。
