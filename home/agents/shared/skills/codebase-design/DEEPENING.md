# 深化

如何在给定依赖的情况下安全地深化一组浅模块。假设你已掌握 [SKILL.md](SKILL.md) 中的词汇表 — **模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估深化候选时，分类其依赖。类别决定深化后的模块如何跨接缝测试。

### 1. 进程内

纯计算，内存状态，无 I/O。始终可深化 — 合并模块并通过新接口直接测试。无需适配器。

### 2. 本地可替换

有本地测试替身的依赖（PGLite 替代 Postgres，内存文件系统）。如果替身存在则可深化。深化后的模块用测试套件中运行的替身测试。接缝是内部的；模块外部接口处无端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的你自己的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

推荐措辞：*"在接缝处定义端口，为生产实现 HTTP 适配器、为测试实现内存适配器，使逻辑位于一个深模块中，即使它跨网络部署。"*

### 4. 真正外部（Mock）

你不控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假设接缝。两个适配器意味着真接缝。** 除非至少有两个适配器被证明合理（通常是生产 + 测试），否则不要引入端口。单适配器接缝只是间接。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（私有于其实现，由其自己的测试使用）以及其接口处的外部接缝。不要因为测试使用内部接缝就通过接口暴露它们。

## 测试策略：替换，而非分层

- 浅模块上的旧单元测试在深化后模块接口处有测试后变为废物 — 删除它们。
- 在深化后模块的接口处写新测试。**接口即测试面**。
- 测试断言通过接口的可观察结果，而非内部状态。
- 测试应在内部重构后存活 — 它们描述行为，而非实现。如果实现变化时测试必须改变，它测试越过了接口。
