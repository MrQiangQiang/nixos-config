
# 代码库设计

设计**深模块**：大量行为在一个小接口背后，放在干净的接缝处，可通过该接口测试。在代码被设计或重构的地方使用此语言和这些原则。目标是为调用者提供杠杆作用，为维护者提供局部性，为所有人提供可测试性。

## 术语表

精确使用这些术语 — 不要替换为"组件"、"服务"、"API"或"边界"。一致的语言是全部意义所在。

**模块（Module）** — 任何有接口和实现的东西。刻意与规模无关：一个函数、类、包或跨层的切片。*避免*：unit、component、service。

**接口（Interface）** — 调用者要正确使用模块必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、所需配置和性能特征。*避免*：API、signature（太窄 — 它们只指类型层面的表面）。

**实现（Implementation）** — 模块内部的东西，其代码体。区别于**适配器（Adapter）**：一个东西可以是小适配器加大实现（Postgres 仓库）或大适配器加小实现（内存假实现）。当接缝是主题时用"适配器"；否则用"实现"。

**深度（Depth）** — 接口处的杠杆作用：调用者（或测试）每单位必须学习的接口能行使的行为量。当大量行为位于小接口背后时模块是**深的**，当接口几乎和实现一样复杂时是**浅的**。

**接缝（Seam）** _(Michael Feathers)_ — 一个你可以不在此处编辑就改变行为的地方；模块接口所在的*位置*。把接缝放在哪里本身是一个设计决策，区别于接缝背后放什么。*避免*：boundary（与 DDD 的限界上下文重载）。

**适配器（Adapter）** — 在接缝处满足接口的具体东西。描述*角色*（填充哪个槽），而非实质（里面是什么）。

**杠杆作用（Leverage）** — 调用者从深度获得的东西：每单位学习的接口获得更多能力。一个实现跨 N 个调用点和 M 个测试回收。

**局部性（Locality）** — 维护者从深度获得的东西：变更、bug、知识和验证集中在一处而非散布在调用者中。修一次，处处修。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，问：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能在内部隐藏更多复杂性吗？

## 原则

- **深度是接口的属性，而非实现的。** 深模块内部可以由小的、可 mock 的、可替换的部分组成 — 它们只是不是接口的一部分。一个模块可以有**内部接缝**（私有于其实现，由其自己的测试使用）以及其接口处的**外部接缝**。
- **删除测试。** 想象删除模块。如果复杂性消失，它是透传的。如果复杂性在 N 个调用者中重现，它在赚取自己的位置。
- **接口即测试面。** 调用者和测试穿过同一接缝。如果你想测试*越过*接口，模块可能形状不对。
- **一个适配器意味着假设接缝。两个适配器意味着真接缝。** 除非有东西真的跨接缝变化，否则不要引入接缝。

## 为可测试性设计

好的接口使测试自然：

1. **接受依赖，不要创建它们。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 更少方法 = 更少测试需要。更少参数 = 更简单测试设置。

## 关系

- 一个**模块**有恰好一个**接口**（它呈现给调用者和测试的表面）。
- **深度**是**模块**的属性，针对其**接口**度量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**并满足**接口**。
- **深度**为调用者产生**杠杆作用**，为维护者产生**局部性**。

## 被拒绝的框架

- **深度为实现行数与接口行数之比**（Ousterhout）：奖励填充实现。我们改用深度即杠杆作用。
- **"接口"作为 TypeScript `interface` 关键字或类的公共方法**：太窄 — 这里的接口包括调用者必须知道的每个事实。
- **"边界（Boundary）"**：与 DDD 的限界上下文重载。说**接缝**或**接口**。
