
# 分诊

通过一个由分诊角色组成的小型状态机，在项目的问题跟踪器上推进 issue。

如果此仓库将外部 pull request 视为一种请求面（见 issue-tracker 配置），分诊也覆盖它们：**PR 是带有附加代码的 issue** — 相同的角色、相同的状态、相同的状态机，下文会标注少量"针对 PR"的差异。按照 tracker 配置将裸的 `#42` 解析为 issue 或 PR。

分诊期间发布到问题跟踪器的每条评论或 issue **必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 角色

两个**分类**角色：

- `bug` — 某物损坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 已完全规格化，准备好交给 AFK agent
- `ready-for-human` — 需要人工实现
- `wontfix` — 不会处理

对于 PR，相同的状态针对附加的代码来解读：`ready-for-agent` 表示已附加简报，agent 应在 diff 上采取下一步；`ready-for-human` 表示已准备好由人工合并。

每个分诊过的 issue 应携带恰好一个分类角色和一个状态角色。如果状态角色冲突，先标记并询问维护者，再做其他事。

这些是规范的角色名 — 问题跟踪器中使用的实际标签字符串可能不同。映射关系应已提供给你 — 如未提供，运行 `/setup-matt-pocock-skills`。

状态转换：未标记的 issue 通常先进入 `needs-triage`；从那里移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。当报告者回复后，`needs-info` 返回到 `needs-triage`。维护者可随时覆盖 — 标记看起来异常的转换并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并执行。示例：

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询问题跟踪器并呈现三个桶，按最旧优先：

1. **未标记** — 从未分诊。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次分诊笔记以来有报告者活动** — 需要重新评估。

当 PR 在范围内时，将这些桶中的外部 PR 一并包含，并在每行标记 `[PR]` 或 `[issue]`。发现只呈现*外部* PR（tracker 配置定义了谁算作外部）— 协作者进行中的 PR 不是分诊工作。此过滤器仅用于发现；明确指定的 PR 无论作者是谁都会被分诊。

显示计数和每条目一行摘要。让维护者选择。

## 分诊特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还包括 diff）。解析任何先前的分诊笔记，以免重复询问已解决的问题。使用项目的领域术语表探索代码库，并尊重该区域的 ADR。对代码库运行两项检查：(a) **冗余** — 按领域概念（而不仅仅是请求的措辞）搜索所请求行为的现有实现，并报告你查看了哪里。如果找到，则是一个已实现的 `wontfix`（步骤 5）。(b) **先前拒绝** — 阅读 `.out-of-scope/*.md` 并呈现任何与此请求相似的记录。

2. **推荐。** 告诉维护者你的分类和状态建议及理由，以及与请求相关的简短代码库摘要 — 包括是否已实现。等待指示。

3. **验证声明。** 在任何盘问之前，检查声明是否成立。对于 bug，按报告者的步骤复现。对于 PR，确认 diff 做了它声称的事 — 检出、运行相关测试或命令。报告发生了什么：确认（带代码路径）、失败或细节不足（强烈的 `needs-info` 信号）。确认的验证会产生强得多的 agent 简报。

4. **盘问（如需要）。** 如果请求需要充实，同时运行 `/grilling` 和 `/domain-modeling` skill — 每次一个问题地将其盘问到成型，在决策落地时同步锐化领域术语并更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 与 agent 简报结构相同，但说明为何无法委托（判断性决策、外部访问、设计决策、人工测试）。
   - `needs-info` — 发布分诊笔记（模板如下）。
   - `wontfix` — 关闭，评论取决于*为何*关闭：
     - **已实现** — 该更改已存在于代码库中。指向其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已构建的）。
     - **已拒绝（bug）** — 礼貌解释，然后关闭。
     - **已拒绝（enhancement）** — 写入 `.out-of-scope/`，从评论链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用角色。如有部分进展可加可选评论。

## 快速状态覆盖

如果维护者说 "move #42 to ready-for-agent"，信任他们并直接应用角色。确认你即将做什么（角色变更、评论、关闭），然后执行。跳过盘问。如果在没有盘问环节的情况下移动到 `ready-for-agent`，询问他们是否想编写 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在"What we've established so far"下捕获盘问期间解决的所有内容，以免工作丢失。问题必须具体且可操作，而不是"please provide more info"。

## 恢复先前的会话

如果 issue 或 PR 上存在先前的分诊笔记，阅读它们，检查报告者是否已回答任何悬而未决的问题，并在继续之前呈现更新的图景。不要重复询问已解决的问题。
