
# 诊断 bug

针对困难 bug 的纪律。仅在明确说明理由时才跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以获得相关模块的清晰心智模型，并检查你所涉及区域的 ADR。

## 阶段 1——构建反馈循环

**这就是这个 skill。** 其他一切都是机械性的。如果你有一个针对该 bug 的**紧凑**通过/失败信号——一个在这个 bug 上会变红的信号——你就会找到原因；二分查找、假设验证和插桩都只是消费它。如果你没有，盯着代码看再多也救不了你。

在这里投入不成比例的精力。**要积极。要创新。拒绝放弃。**

### 构建循环的方法——大致按此顺序尝试

1. **失败的测试**，在任何能触及该 bug 的 seam 处——单元、集成、e2e。
2. **Curl / HTTP 脚本**，对着运行中的开发服务器。
3. **CLI 调用**，输入 fixture，将 stdout 与已知正确的快照对比。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络进行断言。
5. **重放捕获的 trace。** 将真实的网络请求/负载/事件日志保存到磁盘；在隔离环境中通过代码路径重放它。
6. **丢弃式测试装置。** 启动系统的最小子集（一个服务，mock 的依赖），用单个函数调用执行 bug 代码路径。
7. **属性/模糊测试循环。** 如果 bug 是"有时输出错误"，运行 1000 个随机输入并寻找失败模式。
8. **二分测试装置。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动、检查、重复"，这样你就可以 `git bisect run` 它。
9. **差分循环。** 将相同输入通过旧版本 vs 新版本（或两个配置）运行，并对比输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人工点击，用 `scripts/hitl-loop.template.sh` 驱动_他们_，这样循环仍然是结构化的。捕获的输出会反馈给你。

构建正确的反馈循环，bug 就修复了 90%。

### 收紧循环

把循环当作产品对待。一旦你有了_一个_循环，就**收紧**它：

- 我能让它更快吗？（缓存设置，跳过无关的初始化，缩小测试范围。）
- 我能让信号更清晰吗？（断言特定症状，而不是"没崩溃"。）
- 我能让它更确定性吗？（固定时间，设置 RNG 种子，隔离文件系统，冻结网络。）

一个 30 秒的 flake 循环比没有循环好不了多少；一个 2 秒的确定性循环是紧凑的——一种调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。将触发器循环 100 次，并行化，增加压力，缩小时间窗口，注入 sleep。一个 50% flake 的 bug 可以调试；1% 的不行——持续提高复现率直到它可以调试。

### 当你确实无法构建循环时

停下来，明确说明。列出你尝试过的方法。向用户请求：（a）访问能复现它的任何环境，（b）捕获的产物（HAR 文件、日志转储、core dump、带时间戳的屏幕录像），或（c）添加临时生产环境插桩的许可。**不要**在没有循环的情况下继续假设。

### 完成标准——一个变红的紧凑循环

阶段 1 完成于循环是**紧凑的**且**可变红**的：你能说出**一条命令**——一个脚本路径、一个测试调用、一个 curl——你已经**至少运行过一次**（粘贴调用及其输出），并且它：

- [ ] **可变红**——它驱动实际的 bug 代码路径并断言**用户的准确症状**，因此它可以在这个 bug 上变红，修复后变绿。不是"运行不报错"——它必须能_捕获这个特定的 bug_。
- [ ] **确定性**——每次运行结果相同（flake 的 bug：固定的高复现率，见上文）。
- [ ] **快速**——秒级，不是分钟级。
- [ ] **agent 可运行**——你可以无人值守运行它；只有在通过 `scripts/hitl-loop.template.sh` 时才有人参与。

如果你发现自己在命令存在之前就读代码来构建理论，**停下——直接跳到假设正是这个 skill 要防止的失败。** 没有可变红的命令，就没有阶段 2。

## 阶段 2——复现 + 最小化

运行循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生了**用户**描述的失败模式——不是碰巧在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败可跨多次运行复现（或者，对于非确定性 bug，以足够高的复现率可复现以供调试）。
- [ ] 你已捕获准确的症状（错误消息、错误输出、慢的时序），以便后续阶段可以验证修复确实解决了它。

### 最小化

一旦变红，将复现缩小到**仍然变红的最小场景**。一次一个地裁剪输入、调用者、配置、数据和步骤——每次裁剪后重新运行循环——只保留对失败起关键作用的部分。

为什么要费心：最小化的复现缩小了阶段 3 的假设空间（剩下更少的可疑部分），并成为阶段 5 的干净回归测试。

完成于**每个剩余元素都是关键性的**——移除其中任何一个都会让循环变绿。

在复现**并**最小化之前不要继续。

## 阶段 3——假设

在测试任何假设之前，生成**3–5 个排好序的假设**。单一假设的生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

如果你无法陈述预测，假设就是直觉——丢弃或磨砺它。

**在测试之前向用户展示排好序的列表。** 他们通常有领域知识可以立即重排序（"我们刚部署了对 #3 的更改"），或者知道他们已经排除了哪些假设。廉价的检查点，巨大的时间节省。不要阻塞——如果用户 AFK 就按你的排序继续。

## 阶段 4——插桩

每个探针必须映射到阶段 3 的一个特定预测。**一次改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **针对性日志**，放在区分假设的边界处。
3. 永远不要"记录一切然后 grep"。

**为每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最终的清理变成一次 grep。未标记的日志会存活；标记的日志会消亡。

**性能分支。** 对于性能回归，日志通常是错的。取而代之：建立基线测量（时序装置、`performance.now()`、性能分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5——修复 + 回归测试

在修复**之前**编写回归测试——但仅当存在**正确的 seam** 时。

正确的 seam 是测试在调用处以**真实 bug 模式**发生的方式执行的地方。如果唯一可用的 seam 太浅（bug 需要多个调用者时的单调用者测试、无法复现触发 bug 的调用链的单元测试），那里的回归测试会给虚假信心。

**如果没有正确的 seam，这本身就是发现。** 记下来。代码库架构正在阻止 bug 被锁定。为下一阶段标记这一点。

如果存在正确的 seam：

1. 将最小化的复现转换为该 seam 处的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6——清理 + 复盘

声明完成前必须：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或 seam 的缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 丢弃式原型已删除（或移到明确标记的调试位置）
- [ ] 结果正确的假设已写在 commit / PR 消息中——这样下一个调试者可以学习

**然后问：什么会防止这个 bug？** 如果答案涉及架构更改（没有好的测试 seam、纠缠不清的调用者、隐藏的耦合），交给 `/improve-codebase-architecture` skill 并附上具体细节。在修复完成**之后**再提出建议，而不是之前——你现在拥有的信息比开始时更多。
