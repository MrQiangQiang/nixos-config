
# To Tickets

将一个计划、规格或对话拆解为一组**工单**——tracer-bullet 垂直切片，每个声明**阻塞**它的工单。

问题跟踪器和分诊标签词汇应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容开始工作。如果用户传递了一个引用（规格路径、issue 编号或 URL）作为参数，获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，这样做以理解代码的当前状态。工单标题和描述应使用项目的领域术语表词汇，并尊重你所涉及区域的 ADR。

寻找机会预先重构代码以使实现更容易。"让变更变得容易，然后做容易的变更。"

### 3. 起草垂直切片

将工作拆解为 **tracer bullet** 工单。

<vertical-slice-rules>

- 每个切片切出一条狭窄但完整的路径，贯穿每一层（schema、API、UI、测试）——是垂直的，而不是某一层的水平切片
- 一个完成的切片可以独立演示或验证
- 每个切片的大小适合单个全新的上下文窗口
- 任何预先重构应首先完成

</vertical-slice-rules>

为每个工单赋予其**阻塞边界**——必须在它开始之前完成的其他工单。没有阻塞项的工单可以立即开始。

**广泛重构是垂直切片的例外。** 一个**广泛重构**是一次机械式变更——重命名一列、重新定义一个共享符号的类型——其**爆炸半径**波及整个代码库，因此单次编辑就一次破坏数千个调用点，没有垂直切片能落地为绿色。不要把它硬塞进 tracer bullet；将其排序为**扩展–收缩**。先扩展：在旧形式旁边添加新形式，这样不会破坏任何东西。然后按爆炸半径大小（按包、按目录）分批迁移调用点，每批是自己的工单，被扩展工单阻塞，保持 CI 逐批绿色，因为旧形式仍然存在。最后收缩：一旦没有调用方剩余就删除旧形式，在一个被每个迁移批次阻塞的工单中。当即使批次也无法单独保持绿色时，保持顺序但让它们共享一个集成分支，所有这些都阻塞一个最终的集成并验证工单——绿色只在那里被承诺。

### 4. 询问用户

将提议的拆解作为编号列表呈现。对于每个工单，展示：

- **标题**：简短的描述性名称
- **被阻塞于**：哪些其他工单（如果有）必须先完成
- **它交付什么**：此工单使其工作的端到端行为

询问用户：

- 粒度是否合适？（太粗/太细）
- 阻塞边界是否正确——每个工单是否只依赖真正约束它的工单？
- 是否应该合并或进一步拆分某些工单？

迭代直到用户批准该拆解。

### 5. 将工单发布到已配置的跟踪器

发布已批准的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的跟踪器——无论哪种方式工单都是相同的，只是阻塞边界的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每个工单写一个文件，从 `01` 开始按依赖顺序编号（阻塞项在前）。每个文件的"Blocked by"列出它依赖的编号/标题。使用下面的单工单文件模板——每个文件一个工单，绝不是单个合并文件。
- **真实的问题跟踪器（GitHub、Linear……）** → 按依赖顺序（阻塞项在前）每个工单发布一个 issue，这样每个工单的阻塞边界可以引用真实标识符。在平台有原生的阻塞 / 子 issue 关系时使用它；否则将每个工单的"Blocked by"设为阻塞 issue。应用 `ready-for-agent` 分诊标签，除非另有指示——这些工单按构造就是 agent 可认领的。

处理**前沿**：任何阻塞项已全部完成的工单。对于纯线性链条，这意味着从上到下。

不要关闭或修改任何父 issue。

无论哪种形式，避免具体的文件路径或代码片段——它们很快就会过时。例外：如果原型产生了一个比散文更精确地编码决策的片段（状态机、reducer、schema、类型形状），将其内联并简要注明它来自原型。裁剪到决策密集的部分——不是可运行的演示，只是重要的部分。

用 `/implement` 一次处理一个工单的前沿，在工单之间清理上下文。
