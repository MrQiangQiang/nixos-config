
一个松散的想法到来了 — 太大以至于一个 agent 会话无法完成，且笼罩在雾中：从这里到**目的地**的路还看不见。Wayfinding 就是找到那条路，而非直冲目的地。此 skill 将路径绘制为仓库问题跟踪器上的**共享地图**，然后逐个处理其工单，直到路线清晰。

目的地因每次努力而异，而为它命名是绘制地图的第一个动作 — 它塑造每张工单。它可能是一份规格用于交付和迭代，一个决策在规划开始前锁定，或一处就地完成的变更如数据结构迁移。地图与领域无关 — 工程工作、课程内容，任何符合此形状的东西。

## 规划，而非执行

Wayfinder 默认是**规划**：每张工单解决一个决策，当路径清晰时地图就完成了 — 在有人去做这件事之前，没有什么需要再决定。直接去做工作的冲动通常是你已到达地图边缘、该交接的信号。一次努力可以在其 **Notes** 中覆盖此默认 — 将执行带入地图本身 — 但除此之外，产出决策，而非交付物。

## 按名引用

每张地图和工单都是一个 issue，所以它有一个**名字** — 它的标题。在人类阅读的一切内容中 — 叙述、地图的 Decisions-so-far — 用那个名字引用它，绝不用裸的 id、数字或 slug。一墙的 `#42, #43, #44` 是不可读的；名字一眼可读。id 和 URL 不会消失 — 名字包裹其链接 — 但它们*在*名字内部，绝不替代它。

## 地图

地图是此仓库问题跟踪器上的单个 issue，标记为 `wayfinder:map` — 规范产物。其工单是地图的子 issue。

地图是一个**索引**，而非存储。它列出已做出的决策并指向持有细节的工单；一个决策只存在于一个地方 — 它的工单 — 所以地图从不重述它，只摘要并链接。

**地图、其子工单、阻塞关系和前沿查询在物理上位于何处是 tracker 特定的。** 问题跟踪器应已提供给你 — 如未提供，运行 `/setup-matt-pocock-skills`。查阅 tracker 文档的"Wayfinding operations"部分了解*此*仓库如何表达它们。如未提供 tracker，默认使用 local-markdown tracker。

### 地图正文

整个地图的低分辨率视图，每次会话加载一次。打开的工单**不**列出 — 它们是打开的子 issue，通过查询找到。

```markdown
## Destination

<what reaching the end of this map looks like — the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index — one line per closed ticket: enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link) — <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单是地图的**子 issue**；tracker 的 issue id 是其身份。其正文是问题，大小适合一个 100K token 的 agent 会话：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单携带一个 `wayfinder:<type>` 标签 — `research`、`prototype`、`grilling`、`task` 之一（见 [工单类型](#ticket-types)）。

一个会话通过将工单分配给驱动地图的开发者来**认领**它，**首先**，在任何工作之前，这样并发会话会跳过它。那个指派人*就是*认领：一个打开的、未指派的工单是未认领的。

阻塞使用 tracker 的**原生**依赖关系 — 这很关键，因为它在 tracker 自己的 UI 中*可视地*呈现前沿，所以人类不用打开地图就能看到什么可取。只有缺乏原生阻塞的 tracker 才回退到正文约定。一张工单在其每张阻塞工单关闭后**解除阻塞**；**前沿**是打开的、未阻塞的、未认领的子工单 — 已知的边缘。

答案不是正文的一部分 — 它在解决时记录（见 [处理地图](#work-through-the-map)）。解决工单时创建的资产从 issue 链接，而非粘贴其中。

## 工单类型

每张工单要么是 **HITL** — 人在环中，*与*代表自己发言的人一起工作 — 要么是 **AFK**，由 agent 独立驱动。HITL 工单只能通过那次实时交流解决；agent 绝不代替人的那一面（一个回答自己问题的盘问 agent 已经破坏了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或本地资源如知识库。创建一个 markdown 摘要作为链接资产。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：通过制作一个廉价、粗糙、具体的产物来提高讨论的保真度 — 一个大纲、一个粗略草稿、一个桩，或通过 /prototype skill 的 UI/逻辑代码。将原型链接为资产。当"它应该是什么样"或"它应该怎么表现"是关键问题时使用。
- **Grilling**（HITL）：通过 /grilling 和 /domain-modeling skill 对话，每次一个问题。默认情况。
- **Task**（HITL 或 AFK）：在*决策*可以做出之前必须发生的手工工作 — 没什么要决定、原型或调研的，但讨论被阻塞直到它完成。注册一个服务以便其 API 可以被评判、配置访问权限、移动数据以便其形状可见。这是唯一*做*而非*决定*的类型 — 它通过解除一个决策的阻塞来赢得自己的位置，而非通过交付目的地。Agent 能独立做的地方就独立做（AFK）；否则给人类一个精确的检查清单（HITL）。工作完成时解决；答案记录所做的事和任何后续工单依赖的事实（凭证位置、新 URL、行数）。

## 战争迷雾

地图*刻意*不完整：不要绘制你还看不见的东西。活跃工单之外是**战争迷雾** — 你能感觉到即将到来但还无法确定的决策和调查的模糊视图，因为它们依赖于尚未解决的问题。解决一张工单清除其前方的迷雾，将现在可规格化的东西升级为新的工单 — 每次一个，直到到目的地的路清晰且没有工单剩余。

地图的 **Not yet specified** 部分是写下那个模糊视图的地方：疑似问题、以后重访的区域。它是朝向目的地的未发现前沿 — 这里的一切都在范围内，只是还不够清晰到可以开工单。视图允许的范围内松散或完整地写；它兼作路标，供协作者阅读努力的方向。

**迷雾还是工单？** 测试是你现在能否精确陈述问题 — *而非*你现在能否回答它。

- **工单**当问题已经锐利 — 即使它被阻塞且你还不能行动。
- **Not yet specified**当你还无法那么锐利地表述它。不要预先将迷雾切成工单大小的碎片：它比工单粗，一块可能升级为多张工单，或零张，当前沿到达它时。

**Not yet specified**排除已决定的（Decisions so far）、已是活跃工单的、以及范围外的（下一节）。

## 范围外

迷雾只朝目的地聚集。目的地固定范围，所以它之外的工作是**范围外的** — 它不是迷雾，不属于 **Not yet specified**。它在地图上有自己的 **Out of scope** 部分：你有意识排除在*此*努力之外的工作。是范围，而非锐度，把它放在这里。

范围外工作永远不会升级 — 前沿停在目的地 — 所以它只有在目的地重绘时才会返回，且作为新努力，而非续接。

将某事排除在范围外是一个范围划定行为，不是路线上的一步。当一张已存在的工单结果在目的地之外 — 绘制时错误纳入，或被一次解决暴露 — **关闭它**（关闭的工单明确不在前沿）并在 **Out of scope** 部分留一行：摘要加为何范围外，链接到关闭的工单。它不进 **Decisions so far**，后者记录实际走过的路线 — 范围边界不是其中一步。

## 调用

两种模式。无论哪种，**每次会话绝不超过一张工单。**

### 绘制地图

用户用一个松散的想法调用。

1. **命名目的地。** 运行 `/grilling` 和 `/domain-modeling` 会话来确定此地图要找到去哪的路 — 规格、决策或变更。目的地固定范围，所以先确定它。
2. **绘制前沿。** 再次盘问，这次**广度优先**：扇出到整个空间而非深挖任何一条线，呈现开放的决策和现在可取的第一步。**如果这没有呈现迷雾** — 到目的地的路已经清晰，整个旅程小到一次会话可完成 — 你不需要地图。停下来问用户想怎么继续。
3. **创建地图**（标签 `wayfinder:map`）：填入 Destination 和 Notes，Decisions-so-far 为空，迷雾草绘入 **Not yet specified**。
4. **创建你现在可规格化的工单**作为地图的子 issue — 然后在**第二遍**中连接阻塞边（issue 需要 id 才能互相引用）。连接将它们排序为前沿和阻塞的；你尚不能规格化的一切留在迷雾中 — **Not yet specified** 部分。
5. 停 — 绘制地图是一次会话的工作；不要同时解决工单。

### 处理地图

用户用一个地图（URL 或编号）调用。工单是**可选的** — 没有工单时，你选择下一个决策，而非用户。

1. 加载**地图** — 低分辨率视图，不是每张工单正文。
2. 选择工单。如果用户指定了，用它。否则按顺序取第一张前沿工单。**认领它**：在任何工作之前分配给自己。
3. 解决它 — **按需缩放**：按需获取任何相关或已关闭工单的完整正文；调用 `## Notes` 块指定的 skill。如有疑问，用 `/grilling` 和 `/domain-modeling`。
4. 记录解决方案：将答案作为**解决评论**发布，**关闭** issue，并向地图的 Decisions-so-far **追加上下文指针**。
5. 添加新浮现的工单（创建后连接）；升级答案已使其可规格化的任何迷雾，从 **Not yet specified** 中清除每个已升级的块，使其只作为新工单存在。如果答案揭示某张工单 — 此张或他张 — 在目的地之外，**将其排除在范围外**而非在路线上解决。如果决策使地图其他部分失效，更新或删除那些工单。

用户可以并行运行未阻塞的工单，所以预期其他会话并发编辑 tracker。
