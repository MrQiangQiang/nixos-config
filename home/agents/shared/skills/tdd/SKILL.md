
# 测试驱动开发

TDD 就是红 → 绿循环。这个 skill 是让该循环产生值得保留的测试的参考：什么是好测试、测试放在哪里、反模式，以及循环的规则。每个部分都适用于每个周期——在循环之前和期间查阅它们，而不是之后。

探索代码库时，阅读 `CONTEXT.md`（如果存在），以便测试名称和接口词汇与项目的领域语言一致，并遵守你所涉及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。一个好测试读起来就像规格——"用户可以用有效购物车结账"准确告诉你存在什么能力——并且能经受重构，因为它不关心内部结构。

参见 [tests.md](tests.md) 的示例和 [mocking.md](mocking.md) 的 mock 指南。

## Seam——测试放在哪里

**seam** 是你进行测试的公共边界：你观察行为而不深入内部的接口。测试存在于 seam 处，永远不对着内部。

**只在预先约定的 seam 处测试。** 在编写任何测试之前，写下要测试的 seam 并与用户确认。没有测试写在未确认的 seam 上。你无法测试所有东西——预先约定 seam 是让测试精力落在关键路径和复杂逻辑上，而不是每个边缘情况上的方法。

问："公共接口是什么，我们应该测试哪些 seam？"

## 反模式

- **与实现耦合**——mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。特征：当你重构但行为没变时测试会失败。
- **同义反复**——断言按照代码的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手动推导的快照、断言常量等于自身），因此它构造上就通过，永远不可能与代码不一致。期望值必须来自独立的真值来源——已知正确的字面量、一个已推演的示例、规格。
- **横向切片**——先写所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是东西的_形状_而不是面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就承诺了测试结构。改用**纵向切片**工作——一个测试 → 一个实现 → 重复，每个测试都是一颗 **tracer bullet**，响应上一个周期教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。不要预期未来的测试或添加投机性的功能。
- **一次一个切片。** 每个周期一个 seam、一个测试、一个最小实现。
- **重构不是循环的一部分。** 它属于审查阶段（见 `code-review` skill），而不是红 → 绿实现循环。
