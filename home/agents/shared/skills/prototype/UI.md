# UI 原型

在单个路由上生成**几个截然不同的 UI 变体**，通过浮动底栏切换。用户在浏览器中切换变体，选一个（或从每个中偷一点），然后丢弃其余的。

如果问题是关于逻辑/状态而不是东西长什么样——分支选错了。用 [LOGIC.md](LOGIC.md)。

## 什么时候这是对的形态

- "这个页面应该长什么样？"
- "我想在定下来之前看看这个仪表板的几个选项。"
- "试试设置页面的不同布局。"
- 任何用户否则会花一天在脑子里在三个模糊设计稿之间纠结的时候。

## 两种子形态——强烈偏好子形态 A

UI 原型在**紧贴应用其余部分**时——真实头部、真实侧边栏、真实数据、真实密度——更容易评判。一个独立的丢弃式路由是真空：每个变体在孤立中看起来都还行。只要有一个合理的现有页面可以承载变体，就默认用子形态 A。只有当原型确实没有附近的归属时才用子形态 B。

### 子形态 A——对现有页面的调整（首选）

路由已存在。变体渲染在**同一路由**上，由 `?variant=` URL search param 控制。现有的数据获取、参数和认证都保留——只换渲染。这是默认；除非有具体理由否则选它。

如果原型是为还没有页面但*自然会属于某个页面*的东西做的（仪表板的新区块、设置页面的新卡片、现有流程的新步骤）——那仍是子形态 A。在宿主页面内挂载变体。

### 子形态 B——一个新页面（最后手段）

只在被做原型的东西确实没有现有页面可以归属时使用——例如一个全新的顶级界面，或一个无法嵌入任何合理位置的流程。

创建一个**丢弃式路由**，遵循项目已有的路由约定——不要发明新的顶级结构。命名让它显然是原型（例如在路径或文件名中包含 `prototype` 一词）。同样的 `?variant=` 模式。

在定下子形态 B 之前，检查一下：真的没有现有页面可以嵌入吗？空路由会隐藏有内容时暴露的设计问题。

两种子形态中浮动底栏是相同的。

## 流程

### 1. 陈述问题并选 N

默认**3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音——封顶于此。

在一行内写下计划，放在原型位置或文件顶部注释中：

> "设置页面的三个变体，通过 `?variant=` 切换，在现有 `/settings` 路由上。"

无论用户在不在场反驳，这都管用。

### 2. 生成截然不同的变体

起草每个变体。每个都要遵守：

- 页面的目的和它可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须是**结构性不同**——不同的布局、不同的信息层次、不同的主要可供性，不只是颜色不同。三个微调的卡片网格不是 UI 原型，是壁纸。如果两个草稿出来太相似，用明确的"不要用卡片网格"指导重做一个。

### 3. 把它们接在一起

在路由上创建单个切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：在切换器之上保留所有现有的数据获取；每个变体只改变渲染的子树。

子形态 B（新页面）：`/prototype/<name>` 下的丢弃式路由挂载相同的切换器。

### 4. 构建浮动切换器

屏幕底部中间的一个小固定位置栏，有三个部分：

- **左箭头**——循环到上一个变体（环绕）。
- **变体标签**——显示当前变体键，如果变体导出了名称，也显示该名称。例如 `B — 侧边栏布局`。
- **右箭头**——向前循环（环绕）。

行为：

- 点击箭头更新 URL search param（用框架的路由器——Next 用 `router.replace`，React Router 用 `navigate` 等），这样变体是可分享且重载稳定的。
- 键盘：`←` 和 `→` 箭头键也可循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时不要拦截箭头键。
- 视觉上与页面区分（例如高对比度 pill、微妙阴影），这样显然不是被评估设计的一部分。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查控制，这样杂散的原型合并不会把栏发布给用户。

把切换器放在单个共享组件中，这样两种子形态都能复用。放在项目中共享 UI 所在的位置。

### 5. 移交

呈现 URL（和 `?variant=` 键）。用户会在有空时翻看。有趣的反馈通常是**"我想要 B 的头部配 C 的侧边栏"**——那才是他们真正想要的设计。

### 6. 捕获答案并清理

一旦某个变体胜出，捕获答案——哪个变体以及为什么——然后按 [SKILL](SKILL.md) 描述的方式捕获原型。将胜者折入真实代码，其余的移到丢弃式分支，不是 main：

- **子形态 A**——将胜者折入现有页面；从 main 丢弃失败的变体和切换器。
- **子形态 B**——将胜出的变体提升为真实路由；从 main 丢弃丢弃式路由和切换器。

完整的变体集是第一手资料，所以它落在丢弃式分支上，不是垃圾桶——留在 main 分支的变体组件和切换器会很快腐烂并困惑下一个读者。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上不同意。
- **变体之间共享太多代码。** 共享的 `<Header>` 可以；共享的 `<Layout>` 击败了目的。每个变体应该能自由丢弃布局。
- **将变体接到真实 mutation。** 只读原型可以。如果变体需要 mutation，把它指向 stub——问题是"这应该长什么样"，不是"后端是否工作"。
- **将原型直接提升到生产。** 变体代码是在原型约束下写的（无测试、最小错误处理）。折入时正确重写它。
