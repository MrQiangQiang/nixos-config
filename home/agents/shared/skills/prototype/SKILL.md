
# 原型

原型是**回答某个问题的丢弃式代码**。问题决定了形态。

## 选择分支

识别正在回答的是哪个问题——从用户的提示、周围的代码，或者如果用户在的话直接问：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，将状态机推过那些在纸上难以推理的情况。
- **"这应该是什么样的？"** → [UI.md](UI.md)。在单个路由上生成几个截然不同的 UI 变体，通过 URL search param 和浮动底栏切换。

两个分支产生非常不同的产物——选错了会浪费整个原型。如果问题确实模糊且用户联系不上，默认选择更匹配周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型的顶部说明该假设。

## 两者都适用的规则

1. **从第一天起就是丢弃式的，并明确标记为如此。** 将原型代码放在接近实际使用位置的地方（紧邻它为之做原型的模块或页面），这样上下文就显而易见——但命名时让随便看的读者能看出这是原型，不是生产代码。对于丢弃式 UI 路由，遵守项目已有的路由约定；不要发明新的顶级结构。
2. **一条命令运行。** 项目现有任务运行器支持的任何方式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能不假思索地启动它。
3. **默认不持久化。** 状态存在于内存中。持久化是原型_检查_的东西，不是它应该依赖的东西。如果问题明确涉及数据库，用一个 scratch DB 或本地文件，并起一个明确的"PROTOTYPE — wipe me"名称。
4. **跳过打磨。** 没有测试，没有超出让原型_可运行_的错误处理，没有抽象。重点是快速学到东西。
5. **呈现状态。** 每次动作（逻辑）后或每次变体切换（UI）时，打印或渲染完整的相关状态，让用户能看到变化。
6. **完成后捕获它。** 将任何已验证的决定折入真实代码，然后将原型本身作为**第一手资料**捕获：提交到一个丢弃式分支，不在 main 上，并在实现工单上留下指向该分支的上下文指针。也捕获答案——结论和它解决的问题——在工单或 commit 中。main 分支只保留已验证的决定。
