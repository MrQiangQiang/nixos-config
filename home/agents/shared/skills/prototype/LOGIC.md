# 逻辑原型

一个微型交互式终端应用，让用户手动驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用——那种在纸上看起来合理，但只有推过真实情况后才会觉得不对的东西。

## 什么时候这是对的形态

- "我不确定这个状态机是否处理 X 然后 Y 的边缘情况。"
- "这个数据模型是否真的让我能表示……的情况。"
- "我想在写之前先摸索 API 应该是什么样的。"
- 任何用户想**按按钮并看状态变化**的情况。

如果问题是"这应该是什么样的"——分支选错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，写下你正在做原型的是什么状态模型和什么问题。一段话，放在原型的 README 或文件顶部的注释中。回答错误问题的逻辑原型是纯浪费——把问题明确化，以便之后可以检查，无论用户现在在看还是 AFK 后回来。

### 2. 选择语言

使用宿主项目使用的任何语言。如果项目没有明显的运行时（例如文档仓库），问。

匹配项目已有的工具约定——不要只为原型添加新的包管理器或运行时。

### 3. 将逻辑隔离在一个可移植模块中

将实际逻辑——回答问题的那部分——放在一个小的、纯粹的接口后面，该接口以后可以被提取出来并放入真实代码库。围绕它的 TUI 是丢弃式的；逻辑模块不应该是。

正确的形态取决于问题：

- **纯 reducer** —— `(state, action) => state`。当动作是离散事件且状态是单个值时合适。
- **状态机** —— 显式的状态和转换。当"哪些动作现在合法"是问题的一部分时合适。
- **一个普通数据类型上的小集合纯函数**。当没有隐式的当前状态——只有转换时合适。
- **一个有清晰方法表面的类或模块**，当逻辑确实拥有持续的内部状态时。

选择最贴合所问问题的形态，*而不是*最容易接到 TUI 的形态。保持纯粹：没有 I/O，没有终端代码，没有用 `console.log` 做控制流。TUI 导入它并调用它；没有东西反向流动。

这就是让原型在其自身寿命之外有用的原因：当问题被回答后，已验证的 reducer / 状态机 / 函数集可以自行被提取到真实模块中。

### 4. 构建暴露状态的最小 TUI

构建为**轻量级 TUI**——每次 tick，清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价方式）并重新渲染整个帧。用户应该始终看到一个稳定的视图，而不是不断增长的回滚。

每帧有两部分，按此顺序：

1. **当前状态**，格式化打印且便于 diff（每行一个字段，或格式化的 JSON）。字段名或小节标题用**粗体**，不太重要的上下文（时间戳、ID、派生值）用**暗色**。原生 ANSI 转义码即可——`\x1b[1m` 粗体，`\x1b[2m` 暗色，`\x1b[0m` 重置。不需要引入样式库，除非项目已经有了。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 推进时钟  [q] 退出`。粗体显示键，暗色显示描述，或反过来——怎么清晰怎么来。

行为：

1. **初始化状态** —— 单个内存中的对象/结构体。启动时渲染第一帧。
2. **读取一次按键（或一行）**，分发到改变状态的处理函数。
3. **重新渲染** 每次动作后的完整帧——不要追加，要替换。
4. **循环直到退出。**

整个帧应该能放在一屏内。

### 5. 让它一条命令可运行

向项目已有的任务运行器添加脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应该运行 `pnpm run <prototype-name>` 或等价命令——永远不需要记路径。

如果宿主项目没有任务运行器，就把命令放在原型 README 的顶部。

### 6. 移交

把运行命令给用户。他们会自己驱动；有趣的时刻是当他们说"等等，这不应该可能"或"咦，我以为 X 会不一样"——那些是_想法_中的 bug，这正是全部意义所在。如果他们想添加新动作，就添加。原型会演进。

### 7. 捕获答案和原型

一旦原型回答了它的问题，捕获答案，然后按照 [SKILL](SKILL.md) 描述的方式捕获原型。逻辑特定的映射：已验证的 reducer / 状态机 / 函数集被提取到真实模块中（决定，被吸收）；TUI 外壳随丢弃式分支一起保留，让原型作为第一手资料。

## 反模式

- **不要添加测试。** 需要测试的原型不再是原型。
- **不要接到真实数据库。** 使用内存存储，除非问题专门关于持久化。
- **不要泛化。** 不要"如果我们以后想支持 X 怎么办"。原型回答一个问题。
- **不要把逻辑和 TUI 混在一起。** 如果 reducer / 状态机引用了 `console.log`、提示或终端转义码，它就不再可移植。保持 TUI 作为纯模块上的薄外壳。
- **不要把 TUI 外壳发布到生产。** 外壳是为从终端手动驱动而优化的。它背后的逻辑模块才是值得保留的部分。
